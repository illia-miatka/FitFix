# Спайк: чи витримує .NET ядро FitFix

## Питання, на які відповідав спайк

1. Чи читає й пише офіційний Garmin FIT SDK усе, що нам потрібно (позиція, висота, дистанція, пульс, потужність, каденс, температура)?
2. Чи переноситься алгоритм із `prototype/` на C# без втрати результату?
3. Чи можна прибрати жорсткі хаки прототипу (`t > 1720`, поріг 1300 с) на дані-залежні правила?

## Відповіді

**1. SDK — так.** `Garmin.FIT.Sdk` 21.222.0 (NuGet, офіційний пакет Garmin, `Dynastream.Fit`).
Читання — `Decode` + `MesgBroadcaster`, запис — `Encode`. Усі потрібні поля є як
`Get*/Set*` на `RecordMesg`, включно з `EnhancedAltitude` і `EnhancedSpeed`.
Написаний нами FIT читається назад і містить структуру, якої чекає Strava:
`file_id → event(timer start) → record × N → event(timer stop_all) → lap → session → activity`.

**2. Алгоритм — так.** Порт дає ті самі числа, що й Python-прототип.
На синтетичній фікстурі (пробіжка 3,0 м/с, 36 хв, GPS завис на 1300 с):

| Метрика | Значення |
|---|---|
| Дистанція пристрою (до) | 3,90 км |
| Відновлена дистанція | 6,50 км (= довжина треку) |
| Загальний час | 36:00 (збігається з Оригіналом) |
| Темп | 9:13/км → 5:32/км |
| Надійна зона | до 21:35 (60 % активності), 1129 якорів |
| Максимальне відхилення якоря | 3,00 м |
| Висота на старті | 182,8 м (трек був зсунутий на −400,8 м) |

**3. Хаки — прибрані два з трьох.**
- `t > 1720` → `GpsStallDetector`: шукає вікно, де позиція не виходить за 15 м
  протягом ≥ 90 с, при цьому каденс не нульовий (тобто це збій GPS, а не пауза).
  На фікстурі знаходить збій на 1296 с замість зашитих 1720.
- Поріг «1300 с» для нульової потужності → локальне правило: нульову потужність
  відкидаємо лише там, де власна дистанція пристрою не зросла за останні 10 с.
- Пороги швидкості за видом спорту → `AlignmentOptions.ForSport` (біг 7, вело 25, інше 15 м/с).

## Що з'явилось у репозиторії

- `src/FitFix.Core` — чисте ядро: `Geo`, `ReferenceTrack`, `Aligner`, `GpsStallDetector`,
  `RepairService`, читачі/записувач FIT (`Fit/`), читачі GPX і TCX (`Tracks/`)
  з визначенням формату за вмістом файлу.
- `src/FitFix.Cli` — `fitfix repair ОРИГІНАЛ ТРЕК -o РЕЗУЛЬТАТ` (PRD FR-12).
- `tests/FitFix.Core.Tests` — 25 тестів: синтетична фікстура з битим GPS,
  round-trip FIT, читачі треків, і тест на реальній парі файлів
  (тихо виходить, якщо приватних фікстур немає).

## Що лишилось відкритим (у беклог архітектури й сторі)

- **Паузи (timer stop/start).** Не обробляються: під час пауз дистанція не має зростати (FR-5).
  Потрібно читати `event`-повідомлення Оригіналу й виключати паузи з інтерполяції.
- **Кола (laps).** Записуємо одне коло на всю активність; кола Оригіналу треба переносити
  за часом із перерахованими дистанціями (FR-6).
- **Вибір ланцюжка якорів.** Зараз жадібний набір; у PRD закладено «найдовший правдоподібний
  ланцюжок» (DP / LIS з обмеженням швидкості). Жадібний варіант на фікстурі й реальному
  кейсі працює, але на треку-петлі з повторним проходом може збитись.
- **Детектор зависання проти довгої паузи.** Якщо каденсу в Оригіналі немає, детектор
  вважає нерухомість збоєм GPS. Для вело (без каденсу) це може бути помилково.
- **Перевірка на реальних файлах.** `tests/fixtures/private/` порожня —
  `Run_4k_Chabany.fit` і `FFF.fit` треба покласти туди, тоді `PrivateFixtureTests` оживе.
- **`.gitignore` виправлено:** правило `!tests/fixtures/**/*.fit` стояло після заборони
  і повертало приватні GPS-файли в індекс. Тепер приватна тека виключається останньою.

## Зафіксований стек

- Backend: .NET 10 (LTS, локально 10.0.302), ASP.NET Core Minimal API (ще не створено),
  `Garmin.FIT.Sdk` 21.222.0, GPX/TCX через `System.Xml.Linq`.
- Frontend: React 19 + Vite + Tailwind 4, react-leaflet 5, Recharts 3 (Node локально
  ще не встановлений).
- Один Docker-образ: збірка фронту → статика роздається ASP.NET Core.
- Stateless, без акаунтів, локальний `docker compose up` як цільовий спосіб запуску.
